# Item Schema — Design Notes

**Status:** Locked. Schema source of truth: `api/items.py`. Catalog source of truth: `data/catalog/`. Validator: `scripts/validate_catalog.py`.

**Audience:** Future authors (human and AI) working on the item catalog. Read this before refactoring.

---

## Why This Document Exists

The item schema is intentionally **flat**. Every field lives at the top level. There are no nested capability modules, no presence-based discriminators, no per-category sub-schemas with composition rules.

This is a deliberate choice that tends to look wrong to anyone trained on traditional engine design. Past iterations have prototyped a modular alternative (PR #7) and it has been replaced because the modular shape did not fit this system's actual consumers.

If you are reading this because the schema looks unsophisticated and you want to refactor it: **stop and read the rationale section first.** The simplicity is the point.

---

## What The Schema Looks Like

A single Pydantic model `Item` in `api/items.py` with all fields at the top level:

```python
class Item(BaseModel):
    # identity
    id: str
    name: str
    category: ItemCategory          # weapon | armor | shield | ammunition | apparel | gear
    subcategory: Optional[str]
    schema_version: Literal[1]

    # prose (GPT-facing)
    description: str
    narrative_effects: list[str]

    # categorical descriptors
    tags: list[str]
    roll_tag: Optional[str]

    # worldness / economy
    rarity: Rarity
    legality: Legality
    value_cd: int
    wealth_tier_floor: Optional[WealthTierFloor]
    market_tags: list[str]

    # state / consumption
    consumable: bool
    charges_max: Optional[int]

    # combat dispatch
    knowledge_tag: Optional[str]
    application_tag: Optional[str]

    # weapon-specific
    base_damage: Optional[int]
    weapon_handedness: Optional[WeaponHandedness]

    # armor/shield-specific
    armor_floor: Optional[int]
    armor_ceiling: Optional[int]

    # ammunition-specific
    ammo_class: Optional[AmmoClass]
    used_with: list[str]
    bundle_size: Optional[int]
    damage_modifier: Optional[int]
    recoverable: bool
    special_effect_tag: Optional[str]

    # magical-specific
    tier: Optional[ItemTier]        # T0-T5
    magic_field: Optional[str]

    # tool-specific
    tool_role: Optional[ToolRole]   # permission | difficulty-shift
```

Many fields are nullable. Which fields are required is determined by `category` via a model validator (see "Category Gating" below).

---

## Rationale: Why Flat

### Primary consumer is the GPT narrator

The narrator is a Large Language Model that reads items as context, not code that traverses item structures and dispatches on shape. An LLM does not benefit from `if item.modules.weapon is not None`. It benefits from a flat record where every field is named, named consistently, and visible at a glance.

A modular schema like:

```json
{
  "id": "dagger",
  "modules": {
    "weapon": { "weapon_type": "dagger", "damage": [...] },
    "magical": { "effects": [...], "attunement": {...} }
  }
}
```

requires the narrator to traverse a nested structure to figure out what the item is and what it does. A flat schema like:

```json
{
  "id": "dagger",
  "category": "weapon",
  "base_damage": 10,
  "tier": null
}
```

is immediately legible. The LLM reads field-by-field and knows everything.

This is the inverse of what's optimal for traditional code-driven engines. A code-driven engine wants to dispatch on structure; an LLM wants to read prose and labels. The schema is shaped for the consumer.

### Secondary consumer: the GPT builder

The custom GPT narrator gets its tools from the OpenAPI spec generated by FastAPI from the Pydantic models. The GPT builder generates tool parameters from the OpenAPI schema. Flat Pydantic models produce flat tool parameters.

Nested module schemas with `additionalProperties` patterns or discriminated unions degrade tool generation reliability. The GPT builder either fails to expand them or expands them incorrectly. This is a known constraint of the current GPT builder, captured in project memory.

Flat schema = reliable tool parameters = predictable narrator behavior.

### Combat backend dispatches on category, not on module presence

The combat resolution code in the API uses `item.category` plus `item.application_tag` plus `item.knowledge_tag` to route to the right handler. There is no architectural need for nested modules — the discrimination already happens via top-level enum fields.

Adding modules would be solving a problem the code does not have.

## What This Schema Trades Away

A flat schema is honest about its tradeoffs:

1. **Many nullable fields per record.** A torch has `null` for `base_damage`, `armor_floor`, `armor_ceiling`, `ammo_class`, etc. This is verbose but unambiguous.

2. **Category-gated requirements enforced by validator, not by type.** The schema cannot express "if `category == weapon` then `base_damage` must be set" purely structurally; it relies on a `model_validator` to enforce the rule. This is a Pydantic v2 idiom and works reliably.

3. **No structural distinction between mundane and magical items.** A flame tongue longsword is a longsword with `tier: T2` and `magic_field: elemental` set. The "magical-ness" is data, not structure. This is intentional — it keeps both kinds of item readable in the same template.

4. **Cannot easily express composition** ("base item + enchant"). If composition is ever needed, it lives in player inventory state at the database layer, not in the catalog. The catalog only ever holds fully-baked item definitions.

These are not bugs. These are the cost of optimizing for LLM consumers.

## Category Gating Rules

Some fields are required for some categories, forbidden for others. The validator in `api/items.py` enforces these rules. Summary:

| Category | Required fields | Forbidden fields |
|---|---|---|
| `weapon` | `base_damage`, `knowledge_tag`, `application_tag` | — |
| `armor`, `shield` | `armor_floor`, `armor_ceiling`, `knowledge_tag`, `application_tag`; `armor_floor <= armor_ceiling` | — |
| `ammunition` | `ammo_class`, `used_with` (non-empty), `damage_modifier`, `knowledge_tag`, `application_tag` | — |
| `apparel`, `gear` | — | `base_damage`, `armor_floor`, `armor_ceiling`, `ammo_class` |

Cross-cutting rules:

- `tier` set and not `T0` requires `magic_field`. (`T0` is "magically aware but not enchanted" and may omit `magic_field`.)
- `magic_field` set requires `tier` (declare T0-T5 explicitly).
- `charges_max` set requires `consumable: true`.
- `application_tag: unarmored` with `armor_floor > 0` requires `tier T1+` and a `magic_field` set. Mundane unarmored cannot grant armor; only magical garments can armor while preserving martial-arts evasion.

When adding a new category or new combat field, update both `Item._enforce_category_requirements` and this table.

## Vocabularies (Registries)

All controlled vocabularies live at `data/catalog/registries/*.json`. The validator cross-checks every item's references against them. Authoring a value not in the registry is an error.

Active registries (as of locking):

- `item_tags.json` — free-form descriptive tags
- `market_tags.json` — vendor/market category tags
- `combat_knowledge.json` — top-level knowledge groups (parent of applications)
- `combat_applications.json` — specific combat applications (each names its parent `knowledge_group`)
- `magic_fields.json` — magical schools/disciplines
- `item_subcategories.json` — per-category subcategory IDs (e.g. `gear: [light, storage, ...]`)
- `rarities.json` — rarity tiers
- `legality.json` — legality states
- `material_categories.json` — for crafting (currently in registry but crafting subsystem is deferred)
- `biome_types.json` — environment vocabulary

When adding a new field that takes a controlled value, prefer adding a registry over hardcoding the value list. The registry should be the source of truth; the Pydantic Literal type is a convenience for IDE assist and OpenAPI clarity.

## Naming Conventions

Per `docs/conventions.md` and the world-data invariant:

- **File paths and directory names:** `snake_case` (e.g. `data/catalog/items/weapon/flame_tongue_longsword.json`).
- **Content IDs, slugs, and tags:** `kebab-case` (e.g. `id: "flame-tongue-longsword"`).
- **Stem-to-ID rule:** `Path(file).stem == id.replace('-', '_')`. Enforced by `validate_catalog.py`.

The validator also enforces:

- Items live under their category directory: a `category: weapon` item must live in `data/catalog/items/weapon/`.
- IDs are unique across the entire `data/catalog/items/**` namespace.

## What Belongs In The Catalog

The catalog is **type definitions**, not instances.

In: longsword (the type), torch (the type), Flame Tongue Longsword (a named magical archetype anyone could in principle own).

Out: Borin's specific dagger (instance — lives in player inventory or NPC equipment in `data/world/` or the database). The Sword of Drakenvale that exists in exactly one place in lore (instance — lives in `data/world/`). Player gold totals (state — lives in the database).

Rule of thumb: if the same definition could appear in a different campaign with different lore, it's catalog. If it only makes sense in Drakenvale specifically, it's `data/world/`.

---

## What Lives Outside `data/catalog/`

- `data/world/` — specific Drakenvale instances (NPCs, locations, factions, named items).
- `data/characters/` — character creation catalogs (ancestries, backgrounds, cultures, focuses, starting wealth).
- `data/magic/` — spell field definitions.
- `data/companions/` — creature catalog.
- `data/economy/` — top-level economy (currency, prices, regional nodes).
- `data/catalog/registries/` — applications, knowledge groups, magic fields, and other vocabulary registries (consolidated 2026-05 in Brief 23; previously split between `data/tags/` and `data/catalog/registries/`).
- `data/npcs/` — NPC archetypes.

These namespaces were established before the `data/catalog/` consolidation and should be considered for migration into `catalog/` or for explicit "stays separate" status as time permits. They are not in scope for catalog stabilization.

## Deferred Subsystems

These directories exist with README placeholders and will be filled in when their subsystems are designed:

- `data/catalog/services/` — paid actions (lodging, healing, transport, hireling labor)
- `data/catalog/vendors/` — vendor archetypes (smithy, wandering trader, enchanter)
- `data/catalog/crafting/` — partial. `materials.json` is authored (Drakenvale material vocabulary with lore, magical status, scarcity, narrative properties). Used as a worldbuilding/vocabulary reference. Recipes (`recipes.json`) and stations (`stations.json`) are not authored — those constitute the deferred subsystem. Items reference materials by tag (e.g. `tags: [elven-steel]`), not by material ID; that mapping will tighten when recipes ship.

Do not author content into these directories without first designing the subsystem schema. The current README markers are intentional.

## Things That Have Been Considered And Rejected

These are recorded so that future agents do not re-litigate them:

### Modular schema with capability modules

Considered (PR #7, schema with `inventory` / `worldness` / `modules` / `effects` blocks). Rejected because:
- LLM narrator does not benefit from nested structure traversal.
- GPT builder generates tools more reliably from flat Pydantic models.
- Combat backend dispatches on `category` + `application_tag`, not on module presence.
- Migration cost (rewriting authored items) exceeds benefit.

### Effect ID registry with structured `params` validation

Considered. Useful for code-driven mechanics resolution; unnecessary when narrator interprets effects in prose. Magical effects are described in `narrative_effects` and gated by `tier` + `magic_field` + `application_tag`, not by structured effect resolution.

### `source` / `provenance` field per record

Considered. Tracking whether a record came from SRD, original Drakenvale content, or homebrew. Rejected because:
- Git history tracks authorship.
- `data/catalog/` is now Drakenvale-only by policy.
- The `meta` block was an optional escape hatch; no record currently needs it.

### Unit-aware money (currency + amount)

Rejected in favor of integer copper (`value_cd`). Floating-point money causes drift. Display formatting is a presentation concern.

## When To Revisit

The flat schema decision is locked, but it is not eternal. Reconsider if:

1. **The narrator architecture changes.** If item resolution moves from prose interpretation to structured tool dispatch, modules may become useful again.
2. **The GPT builder gains reliable nested-schema support.** Currently it is the bottleneck against nested schemas.
3. **A specific authoring problem cannot be solved within the flat schema.** "We need attunement with multiple slots and recharge cycles and conditional effects" — at some point this is genuinely hard to express as flat fields. If you reach that point, write up the specific blocking case before refactoring.

If you are about to refactor without one of these triggers, the answer is no.

## Maintenance Checklist

When changing the schema:

- [ ] Update `api/items.py` (the Pydantic model and its validator).
- [ ] Update this document if you add a category, change a gating rule, or change naming conventions.
- [ ] Update `scripts/validate_catalog.py` if you add a new vocabulary cross-check.
- [ ] Migrate existing items if you make a backward-incompatible change.
- [ ] Bump `schema_version` and add a migration script if the change is non-trivial.
- [ ] Run `python scripts/validate_catalog.py` and confirm PASS.
- [ ] Update OpenAPI spec via the existing CI guard (`scripts/check_openapi_drift.py`).
